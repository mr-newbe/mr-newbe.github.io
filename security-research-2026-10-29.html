왜 이 논문인가 — 'GET은 읽기, POST는 쓰기'라는 가정이 방어의 기초다

웹 보안의 상당 부분은 메서드 하나로 갈린다는 전제 위에 서 있습니다. 브라우저는 SameSite=Lax 쿠키를 교차 사이트 최상위 이동(top-level navigation)에서 GET일 때만 실어 보냅니다. CDN과 리버스 프록시는 GET 응답만 캐시합니다. WAF 룰셋과 CSRF 토큰 검증, 레이트 리밋은 흔히 "안전한 메서드(GET/HEAD)"를 예외 처리합니다. 즉 방어 장치들이 "상태를 바꾸는 요청은 POST로 온다"는 약속에 기대고 있습니다.

이 논문은 그 약속이 실제 배포된 웹에서는 지켜지지 않는 경우가 적지 않다는 것을, 1만 개 사이트를 직접 두드려서 보여줍니다. 저자들이 정의한 현상은 HTTP 메서드 상호교환성(method interchangeability) — 같은 엔드포인트에 대해 POST 본문 파라미터를 쿼리 스트링으로 옮긴 GET 요청을 보내도 서버가 관찰상 동등한 응답을 돌려주는 경우입니다.

"HTTP method semantics are a common boundary between safe retrieval and state-changing operations; however, deployed web applications do not always enforce this boundary consistently."

중요한 건 이 논문이 "이것 자체가 취약점이다"라고 주장하지 않는다는 점입니다. 읽기 전용 엔드포인트가 GET과 POST를 모두 받아주는 것은 설계상 정당할 수 있습니다. 문제는 그 관대함이 메서드 단위로만 걸린 방어와 만날 때입니다. 저자들의 표현대로, 이것은 "방어·캐시·라우팅 미들웨어·애플리케이션 코드가 세운 가정을 우회할 수 있는 대체 요청 형식"을 노출합니다.

측정 도구 MIDE — '응답이 같다'를 어떻게 믿을 것인가

대규모로 이 현상을 세려면 함정이 하나 있습니다. 서버가 파라미터를 무시해서 응답이 같은 경우와, 파라미터를 실제로 처리해서 응답이 같은 경우를 구분해야 합니다. 전자를 상호교환성으로 세면 결과가 부풀려집니다. 저자들의 파이프라인 MIDE(Method Interchange Detection Engine)는 이 문제를 베이스라인 대조로 해결합니다.

  • ① 브라우저 크롤링: 실제 브라우저(Playwright)로 사이트를 돌며 페이지 로드와 UI 조작이 만들어내는 POST 요청을 캡처합니다. 서비스 워커는 네트워크 이벤트를 가로채므로 차단합니다.
  • ② 후보 변환: 폼 인코딩·JSON 본문을 쿼리 파라미터로 평탄화합니다(JSON은 최대 깊이 2, PHP식 a[] 배열 표기). 깊이 초과나 명시적 null은 손실로 표시합니다.
  • ③ 리플레이 + 베이스라인: 변환한 GET을 재생한 응답을 원 POST 응답과 비교하고, 동시에 파라미터 없는 GET도 보냅니다.
  • ④ 고신뢰 판정: 변환 GET ≡ POST 이면서, 파라미터 없는 GET ≢ POST인 경우만 "고신뢰 상호교환"으로 셉니다. 일반 페이지나 파라미터 무관 응답은 여기서 걸러집니다.
  • ⑤ 안전장치: 파괴적·세션 변경 동작(로그아웃/로그인 등)과 파일 업로드는 경로 키워드·Content-Disposition 검사로 수집 단계에서 제외합니다. 크롤링은 사이트당 10페이지·깊이 5, POST 100개에서 정지.

실험은 인증 없는(unauthenticated) 표면만 대상으로, Tranco 상위 1만 사이트에서 수행됐습니다. 로그인 뒤의 기능은 측정 범위 밖이라는 점이 이 논문의 가장 큰 범위 제한입니다.

결과 — 분모를 바꾸면 4.1%가 14.9%가 된다

같은 407개 사이트를 어떤 모집단으로 나누느냐에 따라 비율이 달라집니다. 이 표가 논문의 핵심 숫자입니다.

모집단크기고신뢰 상호교환 사이트비율
실험한 전체 사이트10,0004074.1%
POST를 1개 이상 캡처한 사이트3,20040712.7%
POST를 GET으로 변환·재생한 사이트2,73440714.9%

더 세밀한 단위로는 재생한 POST 라우트 8,291개 중 646개(7.8%), POST 요청 14,244개 중 1,228개(8.6%)가 고신뢰 상호교환 인스턴스였습니다. 즉 "웹 전체의 4%"라기보다, 상태를 바꾸는 요청을 실제로 관찰할 수 있었던 표면의 8~15%가 메서드를 바꿔도 그대로 동작했다고 읽는 편이 정확합니다.

저자들은 이 현상이 왜 흔한지도 설명합니다. 최신 프레임워크는 URL 경로를 중심으로 라우팅하고 메서드는 부수적으로 검사하는 경우가 많고, 공유 핸들러·관대한 라우팅 설정·메서드를 구분하지 않는 미들웨어가 흔합니다. 브라우저 쪽도 한몫합니다 — 폼이 기본 메서드를 쓰거나 JS가 요청을 재작성할 때 POST가 GET으로 폴백될 수 있습니다.

보안 영향 ① — CSRF 토큰이 '메서드별로만' 검증된다

가장 날카로운 결과는 CSRF 토큰 재생 실험입니다. 저자들은 토큰을 포함한 115개 요청(46개 사이트)을 골라, 일부러 무효 토큰을 넣어 POST와 동등 GET에 각각 보냈습니다.

  • 7건 · 2개 사이트에서 메서드 간 비대칭이 확인됐습니다 — 원래 POST는 무효 토큰을 거부하는데, 동등한 GET은 수용했습니다.
  • 이는 "CSRF 방어가 걸려 있다"는 인상과 달리, GET 경로로는 토큰 검증이 실효적으로 꺼져 있다는 뜻입니다. 표본은 작지만(115건 중 7건), 존재 자체가 메서드 스코프 방어의 구조적 구멍을 보여줍니다.
  • 논문은 이를 로그인 CSRF·세션 고정(session fixation)과 연결해 설명합니다. 인증 상태를 만들거나 세션 ID를 바꾸는 동작이 GET으로 도달 가능하면, 공격자는 이미지 태그 하나, 링크 하나로 피해자의 브라우저를 조종할 수 있습니다. SameSite=Lax가 GET 최상위 이동에 쿠키를 실어 보내는 것과 정확히 맞물립니다.

보안 영향 ② — 캐시 가능한 'POST의 응답'

두 번째 축은 웹 캐시 기만(Web Cache Deception, WCD)입니다. WCD는 원 서버는 URL을 동적·사용자별로 취급하는데 캐시는 같은 URL을 정적 리소스로 취급할 때 성립합니다. 메서드 상호교환이 있으면, 원래는 캐시 대상이 아니어야 할 POST 응답이 GET 리소스로 바뀌어 캐시에 들어갈 수 있습니다.

  • 고신뢰 상호교환 인스턴스 1,228개에 WCD 스타일 검사를 적용한 결과, 9개 사이트의 56개 인스턴스에서 동적 응답이 캐시 가능한 것으로 확인됐습니다.
  • 추가로 50개 사이트의 인스턴스는 변환된 GET URL에서 이미 캐시 가능한 상태였습니다.
  • 논문이 지적하는 근본 원인은 캐시 설정 관행입니다 — 많은 CDN·리버스 프록시가 Cache-Control을 보지 않고 경로에 정적 확장자가 있는지만으로 GET 응답을 캐시합니다. 여기에 "GET만 캐시한다"는 규칙이 겹치면, 메서드 교환이 캐시 가능성의 스위치를 켜버립니다.

원인 분석 — 두 축: '입력 통합'과 '라우트 도달성'

이 논문에서 실무적으로 가장 쓸모 있는 부분은 프레임워크별 비교입니다. 저자들은 상호교환성이 독립적인 두 축의 곱으로 결정된다고 정리합니다.

  • 축 1 — 파라미터 소스 추상화: 쿼리 스트링과 요청 본문을 하나의 인터페이스로 노출하는가. PHP의 $_REQUEST류 통합 접근이 대표적입니다.
  • 축 2 — 라우트 도달성: 라우터가 메서드를 실제로 제약하는가, 아니면 경로만 보고 핸들러를 붙이는가.

결과적으로 바닐라 PHP와 특정 설정의 Spring MVC·ASP.NET Core가 "관대한 라우팅 + 통합/부분 통합 입력 처리"를 겸해 상호교환성에 취약한 조합으로 분류됩니다. 반면 Laravel, Flask, Rails, Sinatra, Gin 등은 같은 동작을 근사하려면 추가 노력이 필요한 쪽입니다. 물론 이는 기본 설정에 대한 분류이지, 개별 애플리케이션이 안전하다는 보장은 아닙니다.

API 기술도 갈립니다. GraphQL과 SPARQL은 읽기 전용 동작에 대해 의도적으로 GET과 POST를 모두 허용하고, 다른 프로토콜은 메서드에 의미를 더 강하게 묶습니다. 즉 "GET/POST 둘 다 받는다"는 사실만으로 취약한 것이 아니라, 그 관대함이 방어 설계와 어긋날 때 문제가 됩니다.

논문이 인정한 한계

  • 인증 없는 표면만 측정: 로그인 후 기능, 권한별 분기, 개인화 응답은 범위 밖입니다. 실제 위험은 인증 뒤에 더 많이 있을 수 있는데 이 실험은 그곳을 보지 못합니다.
  • 응답 동등성은 관찰 기반: 응답 본문·상태 코드의 유사도로 판정하며, 서버 내부 상태가 실제로 변경됐는지는 검증하지 않습니다. (그래서 파괴적 동작을 수집 단계에서 배제합니다.)
  • CSRF 표본이 작음: 토큰 보유 요청 115건, 비대칭 7건. 비율의 일반화보다 현상의 존재 증명으로 읽어야 합니다.
  • 변환의 손실: JSON 깊이 2 초과, 파일 업로드, 명시적 null은 변환에서 빠지거나 손실 표시됩니다. 상호교환성을 과소평가하는 방향의 편향입니다.
  • 단일 스냅샷: Tranco 1만 개를 한 시점에 측정했습니다. 프레임워크 업데이트나 배포 변경에 따른 추이는 알 수 없습니다.

실무 관점 — 방어를 '메서드'가 아니라 '엔드포인트'에 건다

아래는 논문 결과를 운영 관점으로 옮긴 해석입니다(논문의 처방 목록이 아니라 이 글의 정리).

  • CSRF 토큰 검증을 메서드로 분기하지 마세요. "안전한 메서드는 검증 예외"라는 코드가 곧 구멍입니다. 상태를 바꾸는 엔드포인트라면 들어온 메서드와 무관하게 토큰·Origin을 검증하고, 애초에 GET으로 도달 불가능하게 만드세요.
  • 라우터에서 메서드를 명시하세요. 경로만 등록하는 관대한 라우팅은 편하지만, GET/POST 허용 목록을 엔드포인트마다 못 박는 편이 안전합니다. 프레임워크 기본값이 무엇인지 확인하는 것만으로 상당 부분이 드러납니다.
  • 캐시 규칙을 메서드가 아니라 응답으로 정하세요. 확장자 기반 캐시 판정은 WCD의 단골 원인입니다. 인증·개인화 응답에는 Cache-Control: private, no-store를 명시하고, CDN 설정에 "정적 확장자면 캐시" 규칙이 남아 있는지 점검하세요.
  • WAF·레이트리밋 룰도 양쪽 메서드에 겁니다. "POST만 검사"하는 룰셋은 이 논문이 측정한 우회로에 그대로 노출됩니다.
  • 내 자산에도 MIDE류 점검을 돌려볼 수 있습니다. 저자들이 MIT 라이선스로 코드를 공개했으니, 스테이징 환경에서 자사 앱의 POST→GET 변환 가능성을 스캔하는 용도로 쓸 수 있습니다. 운영계에 그대로 돌리는 것은 비권장입니다(논문도 파괴적 동작 배제 필터에 의존합니다).

정리 — 경계는 스펙에 있고, 구현은 그 위에 서 있지 않다

이 논문의 진짜 기여는 새로운 공격 기법이 아니라 측정입니다. "GET은 안전, POST는 상태 변경"이라는 규범이 방어 장치·캐시·브라우저 정책이 공유하는 가정인데, 그 가정이 실제 사이트의 8~15%에서 성립하지 않는다는 것을 베이스라인 대조라는 깔끔한 방법론으로 보여줬습니다.

결론은 단순합니다. 메서드는 스펙의 약속이지 구현의 보장이 아니다. 방어를 메서드 이름에 걸어둔 순간, 그 반대 메서드가 같은 일을 할 수 있는지 확인해야 합니다. 이 논문은 그 확인을 자동화하고, 규모를 재고, 프레임워크별로 원인을 분해했습니다. ACSAC 2026에 게재 예정인 만큼 후속 측정(인증 뒤 표면, 실제 상태 변경 검증)이 이어질 분야입니다.
