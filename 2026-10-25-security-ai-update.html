1. [사건] LiteLLM — “마스터 키를 폐기하지 않았다”, 5월의 커밋 하나가 10월 릴리스 탈취로

어제(10-24) 다룬 LiteLLM 공급망 사고의 근본 원인이 프로젝트 측 사후 분석으로 공개됐다. 핵심은 공격 기법이 아니라 폐기되지 않은 키 하나다. 커밋을 force-push로 덮었지만, 마스터 키만은 회수되지 않은 채 5개월을 살아 있었다.

  • 유입: 2026년 5월 27일 공개 저장소 LiteLLM-Labs/lite-harness에 설정 파일이 커밋되며 LiteLLM Agent Platform 배포의 마스터 키가 함께 올라갔다. 프로젝트는 “오류는 빠르게 발견해 커밋을 덮었고 노출 키는 폐기 대상으로 식별했지만, 마스터 키 폐기는 실제로 이뤄지지 않았다”고 인정했다.
  • 악용: 69.48.229[.]143에서 10월 10일 마스터 키로 플랫폼에 접근, 서비스에 설정돼 있던 GitHub CLI OAuth 토큰을 추출했다. 이 토큰은 권한 범위가 축소되지 않은 상태였고 조직 소유자(owner) 계정에 묶여 있었다.
  • 2단계: 10월 10일 사내 저장소 임시 브랜치에 워크플로를 커밋해 유지보수 권한 엔지니어 2명의 CLI 토큰을 공격자 웹훅으로 빼냈다. 실행 기록은 몇 분 뒤 삭제됐다.
  • 3단계: 10월 21일 브랜치 보호를 우회하고 릴리스 파이프라인의 소스를 유사 이름 저장소 Berri-AI/litellm(정상: BerriAI/litellm)로 바꿔치기. 11:39 버전 1.107.0이 PyPI에 게시되고 11:46 Docker Hub·GHCR 이미지가 배포됐다.
  • 왜 승인이 통과됐나: 원래 릴리스는 승인된 엔지니어가 시작하고 사무실 내 물리 장치에 고정된 특수 계정이 승인해야 했다. 사건 당일 ‘릴리스 빈도 확대’를 위해 이 제한이 엔지니어 2명이면 트리거·승인 가능하도록 완화돼 있었고, 공격자는 탈취한 두 토큰으로 그 조건을 정확히 채웠다.
  • 실무: “비밀을 커밋했으니 force-push로 지웠다”는 대응은 대응이 아니다. 폐기(revoke) 확인이 완료 조건이어야 하고, 배포용 OAuth 토큰은 repo 최소 범위 + 저장소 단위로 좁혀야 한다.

3. [사건] 연구자들이 남의 컴퓨터 200만 대에 ‘업데이트’를 밀어넣었다 — Popcorn Time 업데이터

네덜란드 Eye Security가 2025년 11월~2026년 3월 사이 자기가 소유하지 않은 200만 대 이상의 컴퓨터에 업데이트를 밀어 넣어 백그라운드 업데이터를 원격으로 비활성화했다. 선의의 조치였지만, 그 자체가 ‘공급망을 통한 원격 코드 실행’의 교과서적 시연이 됐다.

  • 발견: 고객 노트북의 Updater.exe가 더 이상 등록되지 않은 도메인을 계속 호출하는 것을 위협 헌팅 중 발견. 해당 도메인은 누구나 선점 가능한 상태였다.
  • 구조: 대상은 2014년 원본이 종료된 뒤 남은 복제판 Time4Popcorn(2025년 초 같은 이름을 쓴 합법 프로젝트와는 무관). 도메인을 선점한 사람은 업데이터를 통해 권한 상승 상태로 악성코드 실행이 가능했고, 이는 대형 봇넷의 기반이 될 수 있었다.
  • 대응: Eye Security는 도메인을 직접 등록한 뒤 서명된 업데이트를 배포해 업데이터를 끄는 방식으로 200만 회 이상 원격 조치를 수행했다.
  • 쟁점: 타인 자산에 대한 무단 원격 변경은 법적·윤리적 회색지대다. 버려진 소프트웨어의 자동 업데이트 경로는 그 자체로 미청구 공격면이며, ‘누가 먼저 도메인을 잡느냐’가 결과를 가른다.
  • 실무: 자산 목록에서 종료된 앱을 지우는 것만으로는 부족하다. 남아 있는 업데이터·에이전트의 콜백 도메인을 DNS 싱크홀·아웃바운드 차단으로 덮어야 한다.

5. [취약점] Brotli 디코더 CVE-2026-111497 — “Node2Shell”, 제품마다 자기 사본을 고쳐야 한다

Google Brotli 디코더의 C 메모리 손상 결함 CVE-2026-111497이 Node.js뿐 아니라 Bun, Python Brotli·brotlicffi, Envoy, Istio까지 확산됐다. Imperva가 미패치 Node.js 24.22.0(리눅스 ARM64)에서 실제 코드 실행을 시연했고, OpenAI Codex Security 팀이 최초 보고했다.

  • 원인: 압축 해제용 C 코드에서 조작된 Brotli 스트림이 버퍼 끝을 넘어 덮어쓴다. 크래시·메모리 유출·공격자 코드 실행으로 이어질 수 있다. 패치는 10월 21일 Node.js와 Google에서 시작됐고 이후 제품별로 이어졌다.
  • 핵심 구조: 결함이 Google 라이브러리에 있지만 각 프로그램이 자기 사본을 내장한다. 런타임 하나만 올려서는 끝나지 않는다.
  • 노출 조건: 남이 제어하는 Brotli 데이터를 디코딩할 때만. Node.js·Bun은 fetch()가 Content-Encoding: br 응답을 읽거나 Express 5·body-parser 2가 br 업로드를 풀 때. Envoy·Istio는 Brotli 압축 해제를 켠 경우에만.
  • Python의 함정: 코드에서 import하지 않아도 brotli 패키지가 설치돼 있으면 requests·urllib3·httpx·aiohttp가 알아서 br 응답을 푼다. 설치 여부 자체가 위험이다.
  • 버전: Google Brotli 1.0.10·1.1.1·1.2.1 / Node.js 22.23.4·24.22.1·26.12.1 / Bun 1.4.4 / Envoy 1.40.0 외 / Istio 1.31.2·1.30.6·1.29.9 / Python brotli 1.2.1 / brotlicffi 1.2.1.0 / cdxgen 13.5.0·12.8.9.
  • WAF 한계: Vercel은 공개 당일 룰을 추가했지만 “함수가 다른 서버에서 가져오는 응답”은 커버하지 못한다고 밝혔다. 그 경로는 런타임·라이브러리 업데이트만이 답이다.

6. [취약점] Ruby Onigmo 버그 3건이 GitLab RCE 4건의 뿌리 — 그런데 Ruby CVE는 없다

Ruby가 4.0.9·3.4.12·3.3.13을 배포해 정규식 엔진 Onigmo의 버그 3건을 고쳤다. 이 버그들이 GitLab이 지난 한 달간 패치한 치명적 RCE 4건의 원인이다. 스캐너 사각지대라는 점이 실무적으로 더 중요하다.

  • 메커니즘: 공격자가 제어하는 문자열로 정규식을 컴파일하는 과정에서 메모리가 손상된다. GitLab은 사용자가 입력한 CI/CD 패턴을 컴파일하므로 그대로 노출됐다.
  • 심각도: 9월 23일 2건은 9.9(로그인 필요), 10월 12일 CVE-2026-97229·10월 21일 CVE-2026-110264는 10.0이며 계정 불필요. 후자는 GitLab 7.0 이후 전 버전에 영향.
  • 고칠 버전: GitLab 19.5.1 / 19.4.3 / 19.3.6 / 19.2.9 / 19.1.9 / 19.0.10 / 18.11.13. Ruby 4.0 사용자는 4.0.8이 아닌 4.0.9여야 한다. Ruby 3.2 이하는 지원 종료(EOL)로 수정 없음.
  • 스캐너 공백: Ruby는 “당분간” 자체 CVE를 신청하지 않았고, GitLab의 CVE 레코드는 영향 제품을 GitLab으로만 적는다. 따라서 “설치된 Ruby 버전”으로 조회하는 스캐너는 매칭할 대상이 없다.
  • 효과 없는 방어: Regexp.timeout 설정은 이 버그를 막지 못하고, 패턴 길이 제한도 짧은 패턴으로 트리거되므로 신뢰할 수 없다. 근본 해결은 신뢰할 수 없는 입력으로 정규식을 컴파일하지 않는 것.

이번 주 패치 뉴스는 ‘고칠 수 있는 것’보다 ‘고칠 수 없게 되는 것’이 많다. 세 건을 묶어 정리한다.

  • Windows Server 2016, 2027년 1월 지원 종료. 이후 보안 업데이트가 중단된다. ESU(확장 보안 업데이트) 없이 남기면 2027년 2월 패치 화요일부터 무패치 상태가 된다. 마이그레이션 리드타임을 역산하면 지금이 설계 시점이다.
  • Microsoft Teams, 11월 초부터 AI 기반 문맥 인식 피싱 탐지. 메시지 문맥을 보고 의심스러운 대화를 판별하는 방식. 탐지가 붙어도 사용자 신고 경로와 외부 테넌트 메시지 정책은 별도로 점검해야 한다.
  • PHP CVE-2026-115560 — 패치 없음, 완화만 제공. PHP2Shell 긴급 패치 이틀 뒤 나온 또 다른 RCE 경로. 비기본(non-default) 설정에서만 영향이며 프로젝트는 “위험 가능성 낮음”으로 보고 긴급 수정을 내지 않는다. 대신 특정 기능을 끄는 완화책을 안내했다.
  • 실무 판단: “낮은 위험”이라는 표현은 기본 설정 기준이다. 커스텀 php.ini·프레임워크 라우팅·레거시 업로드 경로를 쓰는 환경은 스스로 노출 조건을 확인해야 한다.
  • 공통점: 세 건 모두 릴리스 노트를 읽어야만 알 수 있는 항목이다. CVE 피드만 보는 모니터링으로는 EOL·기능 플래그 완화를 놓친다.

10. [트렌드] ‘공유 코드’와 ‘공유 파이프라인’이 동시에 무너졌다 — 10월의 공급망 교훈

이번 주 사건들을 관통하는 구조는 두 가지다. 하나는 같은 코드가 수십 개 제품에 복제되는 것(Brotli·Onigmo), 다른 하나는 릴리스 권한이 사람 한 명의 토큰에 걸리는 것(LiteLLM). 둘 다 ‘우리 코드는 안전하다’는 가정을 무너뜨린다.

  • 복제된 결함: Brotli는 각 런타임이 자기 사본을 내장해 제품 수만큼 패치 창이 생긴다. GitLab 사례에서는 CVE 레코드가 ‘GitLab’만 지목해 Ruby 자체를 스캔하는 도구가 침묵한다. SBOM이 있어도 ‘취약점 DB 매핑’이 끊기면 소용없다.
  • 파이프라인이 곧 신뢰 경계: LiteLLM은 마스터 키 미폐기(5월) → owner 토큰(10/10) → 브랜치 보호 우회 → 유사 저장소로 디플로이어 교체(10/21)로 이어졌다. PyPI 격리까지 약 80분이 걸렸고, 그 사이 1.107.0이 배포됐다.
  • 완화 조치가 공격 창을 열었다: LiteLLM은 릴리스 속도를 위해 ‘물리 장치 고정 계정 승인’을 ‘엔지니어 2인’으로 완화한 직후 공격을 맞았다. 편의를 위한 통제 완화는 반드시 만료일과 함께 적용해야 한다.
  • 버려진 소프트웨어가 미청구 공격면: Popcorn Time 업데이터는 아무도 관리하지 않는 콜백 도메인 하나로 200만 대가 원격 실행 위험에 노출됐다. 자산 목록·EOL 목록·아웃바운드 DNS 차단이 한 세트여야 하는 이유다.
  • 오늘의 결론: “패치했는가”보다 “무엇이 우리 코드 안에 복제돼 있는가”, “릴리스 권한이 몇 개의 토큰에 걸려 있는가”를 먼저 물어야 한다.
