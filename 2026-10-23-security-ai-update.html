1. [사건] Arista VeloCloud Orchestrator CVE-2026-114625 (9.9) — 읽기 전용 계정으로 최고 관리자 권한 탈취, 실제 악용 중

Arista가 10월 22일 VeloCloud Orchestrator(VCO)의 SQL 인젝션 0-day를 공개했다. VCO는 VeloCloud SD-WAN의 중앙 관리 시스템이다. 이 결함은 오케스트레이터에 로그인할 수 있는 사람이라면 가장 낮은 등급인 Enterprise Read Only 계정만 있어도 operator(로컬 슈퍼유저) 권한을 얻을 수 있게 한다. CVSS는 9.9이며 이미 야생에서 악용되고 있다.

  • 3개월 새 세 번째: 7월 CVE-2026-16812, 9월 CVE-2026-93952에 이어 또 하나다. 앞의 두 개는 인증 없이 가능했지만 이번 건은 로그인만 있으면 된다는 점이 다르다 — 즉 자격증명 하나 탈취로 끝난다.
  • 패치 버전: 온프레미스는 VCO 5.2.3.18, 6.1.3.10, 6.4.2.12 이상. Hosted/Dedicated는 이미 패치됨. 주의 — 7월·9월 결함을 고친 릴리스는 이번 결함에는 여전히 취약하다(그 릴리스가 더 오래된 버전이므로). VeloCloud Gateway·Edge는 영향 없음.
  • 노출 특성: VCO 웹 인터페이스는 기본으로 노출되며 이를 막는 VCO 설정이 없다. 그래서 Arista는 업그레이드 전 임시 조치로 ① 관리망에서만 웹 UI 접근 허용 ② 악성 IP 연결 모니터링 ③ VCO 호스트의 비정상 아웃바운드 감시 ④ 불필요 아웃바운드 포트 차단 ⑤ 백도어 데몬·웹셸 점검 ⑥ 관리자 활동 이력 검토를 권고했다.
  • 침해 지표(IoC): 공격에 쓰인 IP 2개 — 74.82.197[.]86, 38.54.50[.]151. 웹 로그에서 URL처럼 보이는 비정상 경로, 인코딩 문자, 내부 서비스 참조, 과도한 요청률을 확인할 것. 침해 의심 시 증거(웹·백엔드·시스템·DB 로그)를 먼저 보존한 뒤 조치하라고 명시했다.

2. [사건] Capcom CAPCOM ID 침해 — 1,170만 계정 이메일·로그인 이력 유출

일본 게임사 Capcom이 자사 통합 계정 서비스 CAPCOM ID가 침해당해 1,170만 건 이상의 고객 이메일과 부가 정보가 유출됐다고 10월 22일 확인했다. 10월 19일 의심스러운 활동을 포착해 20일 침해를 확정했고, 21일 일본 경찰과 개인정보보호위원회에 신고했다.

  • 유출 범위: 이메일 + 계정 생성일, 최종 로그인 시각, 로그인 횟수, 최종 로그인 IP. 일부(43계정)는 생년월일·성별·닉네임·국가까지. 196계정은 비밀번호가 변경돼 소유자를 잠그려는 시도가 있었고 Capcom이 재설정했다. 비밀번호 해시와 신용카드 정보는 유출되지 않았다고 밝혔다.
  • 침투 경로는 비공개: “침입 수법을 확인해 재발 방지 조치를 적용했다”고만 언급했다. 2020년 Ragnar Locker 랜섬웨어(1TB 탈취 주장), 2021년 노후 VPN 장비를 통한 침입 이력이 있는 회사다.
  • 실무 대응: 1,170만 건 규모라 통지는 단계적으로 나간다. CAPCOM ID로 로그인하는 서드파티 연동을 점검하고, 동일 이메일·비밀번호를 재사용한 계정을 전부 교체할 것. 추가 정보나 링크를 요구하는 메일은 피싱으로 간주한다.

6. [취약점] Linux KSMBD CVSS 9.0 RCE 2건 — 커널 수정 전에 공개 메일링리스트로 나왔다

커널 내장 SMB 서버인 KSMBD에서 원격 코드 실행 결함 2건이 공개됐다. Trend Micro ZDI가 9.0으로 평가했고, 메인라인 커널에 아직 수정이 없다. 둘 다 CVE 번호도 아직 없다 — 커널 프로젝트는 안정 트리 수정이 나온 뒤에야 CVE를 부여한다.

  • ZDI-CAN-33774 (인증 불필요): KSMBD 핸들러 테이블 할당의 레이스. 짧은 SMB1 패킷 연속 + SMB2 패킷을 같은 TCP 쓰기에 넣으면, 워커가 SMB1 데이터를 SMB2 핸들러로 처리해 짧은 버퍼 끝을 넘겨 읽는다. 포트 445가 열린 모든 KSMBD 서버가 표적이다.
  • ZDI-CAN-33549 (SMB Direct): SMB Direct 경로의 정수 언더플로. 첫 RDMA 버퍼 기술자가 선언된 페이로드보다 길면 서버 크기 카운터가 감싸 돌고(wrap), 이후 메모리 복사가 할당 버퍼 끝을 넘어 쓴다. 조건은 RDMA 가능 인터페이스(rxe 소프트웨어 드라이버 가능) + 쓰기 가능한 공유 + SMB Direct 협상.
  • 메타 이슈 — 공개된 0-day: ZDI가 패치 없이 공개 리스트에 보고하면서 커널 유지보수진과 마찰이 났다. Greg Kroah-Hartman은 “패치도 없이 공개 리스트로 보냈다면 우리가 할 수 있는 게 없다… 제출 절차를 고쳐달라”고 답했다. 배경에는 2026년 5월 갱신된 커널 보안 문서 — AI 도구가 찾은 버그는 정의상 이미 공개된 것으로 보고 서브시스템 리스트로 보내라는 Linus Torvalds의 지침이 있다. 실제로 이번 건은 TrendAI(AI 스캐너)가 발견자로 크레딧됐다.
  • 확인·대응: systemctl status ksmbd 또는 lsmod | grep ksmbd로 모듈 활성 여부 확인. RHEL은 기본 미포함. 불필요하면 모듈을 내리고, 445를 인터넷에 노출하지 말 것. SMB Direct 수정은 다음 커널 개발 주기용으로 제출됐다는 보도가 있으나 확인되지 않았다.

7. [취약점] OpenCode, 악성 MCP 서버로 로그인 시점 코드 실행 (9.8) — CVE 없음, 스캐너도 못 잡는다

AI 코딩 에이전트 OpenCode에서, 악성 또는 탈취된 MCP 서버가 개발자가 로그인하는 순간 Windows/WSL 머신에서 코드를 실행할 수 있었다. Anomaly는 1.18.33(9월 28일)에서 조용히 고쳤고 CVE도 권고문도 없어 취약 빌드(1.0.137~1.18.32)가 스캐너에 잡히지 않는다.

  • 원리: MCP 로그인(OAuth) 때 서버가 인가 엔드포인트 주소를 직접 준다. Windows/WSL에서 OpenCode는 이 주소를 브라우저 열기 헬퍼에 넘기는데, 헬퍼가 PowerShell 명령을 이스케이프 없이 조립했다. 주소 자리에 PowerShell 명령을 넣으면 그대로 실행된다. macOS/Linux는 셸을 거치지 않아 영향 없다.
  • 트리거 조건: 개발자가 opencode mcp auth 등으로 로그인을 시작할 때만. 서버를 등록만 하거나 세션을 여는 것만으로는 도달하지 않는다. 단, 공격자는 처음부터 적대적일 필요가 없다 — 나중에 탈취되거나 도메인이 넘어간 MCP 서버도 같은 페이로드를 실을 수 있다.
  • 왜 위험한가: Pillar Security가 8월 29일 비공개 보고, 심각도 9.8 제안. Anomaly는 “사용자가 설정한 MCP 서버는 신뢰 경계 밖”이라며 CVE 발급을 거부했다. 수정 PR은 “브라우저 실행 코드 리팩터링”으로만 설명돼 보안 수정임이 드러나지 않았다. 2025년 7월 mcp-remote의 거의 동일한 결함(CVE-2025-6514)과 같은 계열이다.
  • 조치: OpenCode 1.18.33 이상으로 업그레이드. 불가하면 검증하지 않은 원격 MCP 서버를 설정에서 제거. “https 주소인지 확인” 같은 통상 방어는 통하지 않는다(공격도 평범한 HTTPS 주소를 쓴다).

8. [취약점] AI 에이전트 프레임워크가 새 공격면 — 무인증 RCE 9.8이 한 주에 6건

NVD 최근 3일(10/20~10/23, 총 2,965건) 상위를 보면 CVSS 9.8 무인증 RCE가 AI 에이전트·LLM 프레임워크에 몰려 있다. 공통 원인은 “기본 설정이 인증을 안 건다”와 “에이전트에게 셸 도구를 그냥 준다”이다.

  • CVE-2026-77932 DB-GPT ≤0.8.2 (9.8): /api/v1/chat/react-agent가 목(mock) get_user_from_headers에 의존해 모든 호출자에게 admin 역할을 준다. 인증 없이 RCE.
  • CVE-2026-77933 DB-GPT (9.8): 기본 docker-compose.yml에 고정 MySQL root 비밀번호 + 3306 전체 인터페이스 공개.

9. [패치] eMudhra, 글로벌 SSL/TLS 사업 철수 — Chrome·Firefox 루트 불신, 3.08만 인증서 교체 필요

인도 CA eMudhra가 이사회 결정으로 글로벌 SSL/TLS 인증서 사업에서 철수한다고 밝혔다. 연구자가 중간 CA 8개의 개인키를 복구했다고 보고한 지 5일 만이다. 8개 중 6개가 웹(TLS)용이었고, Chrome은 상위 루트 emSign ECC Root CA - G3를 10월 27일 오전(태평양시간)부터 신뢰하지 않는다. Mozilla는 10월 20일 이미 Firefox에서 같은 루트를 제거하기로 했다.

  • 왜 이렇게 됐나: 개인키는 거대한 난수여야 하는데 8개 모두 256 미만이었다 — 사실상 누구나 몇 초에 계산할 수 있는 값. Chrome·Firefox는 6개 TLS 중간 CA를 몇 시간 만에 차단했다. 다행히 차단 전까지 CT 로그에 이 중간 CA로 발급된 웹 인증서는 없었다고 Google은 밝혔다. eMudhra는 시스템 침해나 실제 발급 사실은 없다고 주장한다.
  • 규모: 10월 21일 기준 해당 루트에 연결된 미만료 인증서 약 30,800장. 그중 99.9%가 InCommon(Internet2의 고등교육 인증서 서비스)을 통해 발급됐다 — InCommon이 올해 4~7월에 eMudhra의 CertiNext 플랫폼으로 옮긴 결과다. 코넬은 자체 300여 장, 미시간대 등 미국 대학들이 직격탄.
  • 즉시 조치: Google은 해당 루트 아래 인증서를 쓰는 사이트에 “Chrome 루트 스토어에 포함된 다른 PKI에서 새 TLS 인증서를 즉시 발급·설치하라”고 명시했다. 대학들은 RSA 인증서로 전환 권고(별도 루트인 G1 계열은 현재 영향 없음) 또는 Let's Encrypt로 이동. 약 97%가 ACME로 발급됐지만, ACME 클라이언트는 갱신 주기가 아닌 인증서를 자동 교체하지 않는다(ARI 미지원 시) — 수동 개입이 필요하다.
  • 남는 리스크: Chrome은 G1 RSA 루트까지 루트 스토어에서 뺄지 아직 결정 중이다. 전자서명·eSign·CertiNext 사업은 계속되지만, G1에 의존하는 인증서도 대체 경로를 미리 확보해 두는 것이 안전하다. eMudhra는 폐기·상태 서비스를 모든 인증서가 만료·교체될 때까지 유지한다.

10. [패치] Chrome, Gemini 서버측 사기 탐지 + ClickFix 클립보드 경고

Chrome의 Safe Browsing Enhanced Protection이 Gemini 기반 사기 탐지를 서버측으로 확장하고, ClickFix 공격용 명령을 사용자가 복사하는 순간을 잡아낸다. Google은 표준 보호 대비 피싱·소셜 엔지니어링·알림 악용에서 10배 안전하다고 주장한다.

  • 서버측 모델로 이동: 기존 온디바이스 Gemini를 Enhanced Protection 사용자에 한해 더 큰 서버 모델로 교체. 페이지의 브랜드·의도·사기 가능성을 신호로 보고 도메인 평판 등과 결합한다. “고신뢰 사기 지표가 있을 때만 페이지 텍스트를 분석”하고, 전송된 내용은 일시 처리(ephemeral) — 기록·보관·학습에 쓰지 않는다고 밝혔다.
  • “suspicious site” 경고 신설: 전체 화면 빨간 경고를 띄울 확신도까지는 못 미치지만 기만적 패턴을 보이는 페이지에 별도 UI로 경고한다. 경고 UI를 세분화해 더 많은 페이지에 보호 경고를 넓히겠다는 전략.
  • ClickFix 차단: 사용자가 직접 PowerShell/CMD 명령을 붙여넣게 만드는 수법을 겨냥. 클립보드 페이로드에서 개인식별정보를 제거한 뒤 Safe Browsing에 보내 분석하고, 위험 판정이면 진행 전에 경고한다.
  • 실무 메모: 이 기능은 Enhanced Protection 옵트인에서만 동작한다. 기업은 정책으로 켜야 하고, 켜면 페이지 텍스트 일부가 Google로 전송된다는 점을 개인정보 검토에 반영해야 한다(일시 처리 고지). KEV 마감도 계속 확인 — 최근 항목은 Ivanti Connect Secure 인증 우회(CVE-2026-104935, 10/16 마감), Microsoft Windows 명령 주입(CVE-2026-96951, 10/16), PAN-OS 코드 주입(CVE-2026-0322, 10/17), Cisco Secure Email Gateway 경로 순회(CVE-2026-76519, 10/17), AhsayCBS 인증 우회(CVE-2026-105133, 10/17).

11. [트렌드] ‘Black October’ — AI가 찾은 취약점이 패치보다 먼저 악용된다

10월 한 달의 패턴이 뚜렷해졌다. AI가 대규모로 찾아낸 취약점이 패치 공개 전에 이미 공격에 쓰이고, 방어자는 “패치·배포·검증”이라는 사람 속도에 갇힌다. Amazon Threat Intelligence는 PHP2Shell 결함 악용이 패치 공개 4일 전에 시작됐다고 밝혔다. 같은 주에 GitLab 10.0, PHP 긴급 패치, LiteLLM 공급망 침해, KSMBD 9.0 무패치 공개가 겹쳤다.

  • 공격도 자동화로 맞선다: BleepingComputer가 정리한 “machine speed” 분석에 따르면 자격증명 탈취에서 데이터 유출 시작까지 몇 분이면 끝난다. 탈취된 GitHub 토큰, 악성 AI 설치 프로그램, MFA 피싱이 대표 경로다. 유효 자격증명을 잡은 뒤에는 공격자 행동의 63%가 차단되지 않는다는 벤더 측정도 있다 — 예방 점수는 초기 침투 이후를 설명하지 못한다.
  • 공급망이 새 기본값: LiteLLM은 PyPI 패키지와 Docker 이미지가 동시에 오염됐고, 회사는 AI 게이트웨이 로그에 남은 GitHub 토큰 유출을 의심한다. Railway 사례까지 겹치면 “개발자 플랫폼·AI 게이트웨이의 시크릿”이 최우선 표적이다.
  • AI가 취약점을 찾는 속도가 규제·공개 절차를 압박한다: KSMBD 건에서 ZDI는 AI 스캐너(TrendAI)가 찾은 버그를 커널 지침대로 공개 리스트에 올렸고, 패치 없는 0-day가 그대로 노출됐다. “AI가 찾으면 이미 공개된 것”이라는 2026년 커널 정책과 “조율된 공개” 원칙이 충돌하는 지점이다.
  • 그래서 우선순위는: ① 엣지·관리 평면(VCO, VPN, 방화벽, Kubernetes Console)부터 패치 — 이번 주 고위험은 전부 여기다 ② 시크릿 위생: 환경변수·CI 토큰·패키지 배포 권한을 짧은 수명·자동 로테이션으로 ③ AI 에이전트 런타임을 인터넷에서 격리하고 셸 도구에 승인 게이트 ④ PKI 인벤토리 관리(10/27 eMudhra 루트 불신 D-day) ⑤ 탐지·격리를 자동화해 “사람 속도” 구간을 줄이기 ⑥ AI가 찾은 취약점이 곧 공개된다는 전제로 패치 SLA를 시간 단위로 재설계.
