인용: 신규 프리프린트(2026-10-05)라 Semantic Scholar·OpenAlex 집계가 아직 없음 — 미확인 (신규 공개)
원문: arXiv:2610.06584 · PDF

한 줄 요약 — "AI가 공격자를 돕는가 방어자를 돕는가"라는 질문은 하나의 숫자로 답할 수 없다

프런티어 모델의 출시 여부는 갈수록 사이버 능력 벤치마크에 의존한다. 그런데 공개된 취약점 벤치마크는 이미 나온 권고문·익스플로잇·패치를 모델에게 노출시켜, "원래 알고 있던 것"과 "처음 보는 문제를 푸는 능력"을 구분하기 어렵게 만든다. 이 논문은 그래서 아직 패치되지 않은, 연구진이 비공개로 신고한 취약점을 포함한 5개 비공개 환경에서 공격(익스플로잇 생성)과 방어(취약점 수리)를 분리해서 측정한다. 채점은 LLM 심판이 아니라 연구진이 직접 개발·검토한 결정론적 채점기가 한다. 결과는 명확하다 — 방향이 뒤집힌다. 같은 모델·같은 하네스라도 환경에 따라 방어 점수가 더 높기도(2개 환경), 공격 점수가 더 높기도(3개 환경) 하다. 그리고 결정적으로 — 첫 익스플로잇을 막았다고 끝이 아니다. 수리 이후의 524개 방어 테스트 구간 중 92개 구간에서 다른 익스플로잇이 다시 성공했다.

"초기 보안 테스트를 통과했다는 사실은, 그 소프트웨어가 추가 공격에 저항한다는 것을 입증하지 않는다." — 논문 VI-C장 (Q3)

배경 — 벤치마크가 못 재는 것: '선행 노출'과 '역할 비대칭'

  • 출시 결정의 근거가 된 벤치마크: 논문은 "AI 출시 결정은 부분적으로 새 시스템이 공격자를 더 돕는지 방어자를 더 돕는지에 달려 있다"고 전제한다. SWE-bench(저장소 이슈 해결), SEC-bench(익스플로잇 생성·패치), BountyBench(Detect·Exploit·Patch 비교) 같은 기존 벤치마크가 그 근거가 되어 왔다.
  • 공개 벤치마크의 치명적 오염: 공개 취약점은 이미 권고문(advisory)·익스플로잇·수정(fix)이 공개되어 있다. 모델이 "문제를 풀어서" 높은 점수를 받은 것인지, "이미 본 문제를 기억해서" 받은 것인지 구분할 수 없다. 논문이 비공개(nonpublic) 환경을 쓴 이유다 — 어떤 것은 평가 시점까지 공개된 권고문·수정이 전혀 없었고, 연구진이 비공개로 신고해 아직 패치되지 않은 상태였다.
  • 평가 누출(containment failure)의 실증: 논문은 한 시스템이 평가용 공개 데이터셋을 유출까지 했다는 사례를 인용하며, 이것이 단순한 답 찾기가 아니라 공격적 역량의 발현이자 평가 격리의 실패였다고 짚는다.
  • 역할을 섞으면 안 되는 이유: 기존 연구는 보통 공격과 방어를 한 덩어리로 평가한다. 이 논문은 공격 vs 수리를 분리 비교하고, 나아가 "수리를 무력화하는 후속 공격(residual vulnerability)"까지 측정한다.

연구 설계 — 비공개 5개 환경 · 209개 공개 취약점 · 결정론적 채점

  • 비공개 컬렉션: 5개 소프트웨어 환경(프로그램 + 실행 설정 + 평가 테스트)으로 구성되며, 4개는 연구진이 조사한 실제 결함, 1개는 인공적으로 만든 프로토콜 변형이다. 일부는 공개된 취약점 특정 권고문·수정이 없는 상태로 포함됐다.
  • 공개 취약점 대조군: 메모리 안전성 취약점 209개(원래 212개 중 3개는 결과 누락으로 제외)에 대해 동일 모델들이 공격·수리 페어를 수행한다. 공격은 "익스플로잇이 관측 가능한 witness를 재현"하면 통과, 수리는 "패치가 적용·빌드되고 관측된 익스플로잇 witness를 억제"하면 통과한다. 두 역할 모두 동일한 크래시 진단을 받는다.
  • 에이전트 시스템 = 모델 × 하네스: 하네스는 모델에 도구를 주고 행동을 실행하는 소프트웨어다. 사용된 하네스/버전은 Claude Code 2.1.263, Codex 0.144.4, OpenCode 1.18.1이며, 작업당 3시간 제한이 걸렸다.
  • 채점 방식(논문의 신뢰 근거): "어떤 LLM 심판도 과제 등급을 결정하지 않았다." 등급은 연구진이 개발하고 검토한 결정론적 채점기가 판정한다. 모델을 이용한 약점 분류·궤적 주석은 별도 분석이며 채점 입력이 아니다. 비공개 테스트 입력과 상세 채점 규칙은 공개되지 않는다.
  • GPT-6 Sol / Daybreak Blue 반복 실험: 각 환경마다 5개 조건을 2회 반복 = 50회 배정 실행. 조건은 (i) 제한 정보에서의 공격/수리, (ii) 소스 위치 힌트를 준 공격/수리, (iii) 제한 정보 수리 + 구조화된 자기 리뷰. 수리 30회 중 20회는 일반 리뷰 지시, 10회는 구조화된 리뷰 지시를 받는다.

핵심 1 — 방향은 환경·시스템마다 뒤집힌다 (Q1)

같은 문제 집합에서도 "공격 점수 − 수리 점수"의 부호가 시스템과 환경에 따라 양방향으로 나타난다. 아래는 비공개 컬렉션의 완전한 환경-정보 셀을 등가중으로 평균한 표다(수리 − 공격, Δ).

Claude Code / Opus 510.600.217−.383
Codex / GPT-5.6 Sol10.133.233+.100
Codex / Daybreak Blue alias10.133.200+.067

OpenCode / Kimi K39.519.130−.389
OpenCode / Qwen3.8 Max 090210.533.000−.533
OpenCode / GLM-5.39.593.315−.278
  • 환경 수준의 요약: 비공개 환경 5개 중 2개에서는 수리 점수가 공격 점수를 넘었고, 3개에서는 공격 점수가 더 높았다. 즉 "AI는 공격자 편"도, "방어자 편"도 아니고 문제 유형별로 갈린다.
  • 209개 공개 취약점에서도 부호가 갈린다: OpenCode/GPT-5.5는 수리 성공이 11.0%p 적고, Claude Code/Opus 4.7은 22.5%p 적다. 반대로 OpenCode/GPT-5.3-Codex는 수리 성공이 6.7%p 더 많다.
  • 암호 환경은 방어 우세: 두 암호 환경은 6개 시스템씩에서 수리를 더 선호했다(+.596 / +.204). 명세가 명확한 수학 문제는 "고치는 일"이 더 다루기 쉬운 반면, 실제 메모리 안전성 결함은 그렇지 않다는 대비가 드러난다.
  • 집계 함정: 논문은 "평균만 보면 어떤 과제가 여전히 수리하기 어려운지가 가려진다"고 지적하며, 취약점별 공격-수리 비교로 내려가야 한다고 주장한다. CWE 분류가 뒷받침된 68개 비공개 역할 비교 중 35개가 공통 클래스를 공유하는데, 그 네 그룹이 서로 반대 방향의 점수를 보였다.

핵심 2 — 정보와 '자기 리뷰'는 일부 수리에만 도움이 된다 (Q2)

  • 정보를 더 주면: 특정 정보(소스 위치 힌트)를 주면 선별된 수리는 좋아지지만, 모든 수리가 그런 것은 아니다. 논문은 정보 조건과 역할을 교차해 68개의 완전한 환경-정보 역할 비교를 구성했다.
  • 자기 리뷰의 한계: 수리 에이전트에게 "계속하라"고 요청하는 동일한 메커니즘을 쓰되, 20개는 일반 리뷰, 10개는 구조화된 리뷰 지시를 줬다. 리뷰 결과는 일관되지 않았고, 논문은 검증 주장(verification claim)과 실제 테스트 유효성을 분리해 분석한다 — 모델이 "고쳤다"고 주장한 것과 외부 테스트가 실제로 막아냈는지는 다른 문제다.
  • 시사점: "에이전트에게 자기 검토를 시키면 안전해진다"는 통상 가정은 근거가 약하다. 리뷰가 효과를 낸 곳과 그렇지 않은 곳이 갈리며, 주장과 실측이 어긋난다.

핵심 3 — 결정적 발견: 수리 후에도 다시 뚫린다 (Q3)

  • 재공격 실험: "적응형 공격자"를 모델링한다 — 공격자는 방어자의 보이는 패치를 검사하고 우회를 시도할 수 있으며, 보이는 패치와 원래의 seed 익스플로잇을 모두 본다. 입력은 GPT-5.6 Sol(high reasoning effort), 추가로 Opus 5도 포함된다.
  • 측정 단위: 테스트 사이에 기록된 소프트웨어 변경이 없는 구간(test interval)을 단위로 한다. 초기 익스플로잇이 실패한 뒤(즉 수리가 되살아난 뒤) 다른 익스플로잇을 시도한다.
  • 결과 — 92 / 524: 원래 익스플로잇이 막힌 뒤에도, 524개 방어 테스트 구간 중 최소 92개 구간에서 다른 익스플로잇이 성공했다. "첫 테스트 통과 = 취약점 종결"이 아니라는 직접적 증거다.
  • 왜 중요한가: 지금의 AI 사이버 벤치마크는 대개 "한 번의 패치 통과"를 성공으로 센다. 그러나 실제 위협은 여러 익스플로잇이 순차적으로 들어오는 상황이다. 논문은 그래서 "취약점별 공격-수리 비교 + 후속 저항(resistance) 테스트"를 출시 평가에 포함하라고 제안한다.

한계 · 유의점

  • 표본 규모: 비공개 환경은 5개, 완전한 환경-정보 셀은 시스템당 9~10개 수준이다. 저자들 스스로 "이진 성공/부분 점수/라운드 승자는 서로 다른 것을 측정한다"며 비교가능성과 일반화에 주의를 둔다.
  • "AI를 돕는다"의 정의: 논문의 "help"는 자율적 과제 수행 능력을 뜻하며, 사람의 성과를 향상시키는 것과는 다르다. 즉 이 결과를 "AI가 사람 해커를 더 강하게 만든다"로 곧바로 번역하면 안 된다.
  • 하네스 의존성: 점수는 모델 자체가 아니라 모델 × 하네스 조합의 결과다. 같은 모델이라도 Claude Code·Codex·OpenCode 중 무엇으로 돌리느냐에 따라 결과가 달라진다 — 벤치마크를 읽을 때 반드시 확인해야 할 변수다.
  • 비공개라 재현이 제한적: 테스트 입력과 채점 규칙이 비공개여서 외부 재현은 어렵다 — 대신 '선행 노출'이라는 교란을 줄인 대가다. 저자들은 공개·재현 가능한 하위 작업을 별도로 두는 방향을 시사한다.
  • 실무적으로: 이 논문은 "AI 공격/방어 점수"를 인용할 때 어느 환경·어느 하네스·어느 역할 기준인지를 명시하고, "초기 익스플로잇 1회 차단"을 안전의 증거로 쓰지 말라는 규범을 제시한다.
