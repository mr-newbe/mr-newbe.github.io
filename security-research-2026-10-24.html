왜 이 논문인가 — "정확도는 그대로인데 느려졌다"는 가장 찾기 어려운 공격

LLM 서빙에서 보통 공격자는 모델 가중치를 노립니다. 비트를 뒤집어 답을 틀리게 만들거나, 백도어를 심거나, 컨텍스트를 빼냅니다. 그런 공격은 출력이 이상해지므로 결국 누군가 알아챕니다.

IIT Bombay의 Shukla·Roy·Panda가 10월 22일 올린 LLVMhammer는 정반대를 겨냥합니다. 뒤집는 대상은 모델도, GPU 메모리도 아닙니다. CPU DRAM에 올라와 있는 Triton 컴파일러 라이브러리(libtriton.so)입니다. 결과는 기능적으로 완전히 동일하지만 더 느린 GPU 커널 — 정확도 지표는 흔들리지 않고, TTFT·TPOT·처리량만 조금씩 나빠집니다.

논문의 한 줄 요약: "공격자는 코드를 바꾸지 않고, 컴파일러가 내리는 '최적화 결정'만 바꾼다." 그리고 Triton은 커널을 ~/.triton/cache에 저장하므로, 비트플립 한 번이 프로세스를 재시작해도 계속 남습니다.

위협 모델 — 같은 물리 호스트의 '평범한' 공동 테넌트

  • 피해자: 공유 물리 호스트에서 LLM 추론 서비스를 운영. Triton으로 GPU 커널을 JIT 컴파일하고 vLLM으로 서빙. 모델 가중치는 공격자에게 노출되지 않고, Triton/MLIR/LLVM 소스도 신뢰된 배포판 그대로입니다.
  • 공격자: 같은 머신에서 도는 비특권 사용자 프로세스. 피해자 메모리·가중치·추론 설정을 읽거나 쓸 수 없습니다. 다만 자기 주소 공간의 물리 DRAM 페이지를 잡고 Rowhammer를 걸 수 있습니다 — PRowhammer 등이 확립한 클라우드 공동 테넌시 모델 그대로입니다.
  • 핵심 전제: Triton은 공유 라이브러리로 배포됩니다. 메모리 중복제거(deduplication)나 메모리 마사징으로 피해자의 libtriton.so 페이지를 공격자가 겨냥할 수 있다는 것이 선행 연구의 결론이고, 이 논문은 그 위에 올라탑니다.
  • 공격 목표: 기밀성도 무결성도 아닌 효율성입니다. 논문은 이를 "inference efficiency attack"으로 부르고, 정확도 저하 공격(DeepHammer 계열)과 명확히 구분합니다.

메커니즘 — 128비트 로드를 4개의 스칼라 로드로 바꾸는 '한 비트'

Triton은 Python DSL에서 시작해 MLIR → LLVM IR → PTX/AMDGCN → 기계어로 내려가는 파이프라인을 씁니다. 이 중 타깃 독립 단계(Triton IR·Triton-GPU IR 최적화)는 NVIDIA·AMD 백엔드가 공통으로 소비하는 표현입니다. 여기에 비트 하나가 뒤집히면, 벤더별 백엔드에 도달하기 전에 이미 잘못된 최적화 결정이 굳어집니다.

단계정상 커널비트플립 후
LLVM IRld.global.v4.b32 — 128비트 벡터 로드 1회ld.global.b32 × 4 — 스칼라 로드 4회
PTX128비트 코얼레스드 로드/스토어32비트 로드 4개, 메모리 트랜잭션 4배
SASSLDG.E.128스칼라 LDG 여러 개
  • 왜 정확도는 그대로인가: 벡터 로드를 스칼라로 쪼개도 산술 결과는 같습니다. 바뀌는 것은 메모리 트랜잭션 수와 대역폭 효율뿐입니다. 그래서 출력 검증·정확도 모니터링으로는 잡히지 않습니다.
  • 왜 영구적인가: Triton은 컴파일된 커널을 온디스크 캐시에 저장하고 다음 요청에서 재사용합니다. 비트플립이 만든 준최적 커널이 캐시에 들어가면, 프로세스를 재시작해도 계속 그 커널이 로드됩니다.
  • 왜 벤더 무관인가: 공격 지점이 NVIDIA SASS가 아니라 타깃 독립 IR 단계이기 때문입니다. PRowhammer가 NVIDIA SASS 프로파일링에 묶여 있던 것과 대비되는 이 논문의 핵심 주장입니다.

Karnage — 118만 개 후보를 1,176개로 줄이는 자동화

libtriton.so에는 12만 개가 넘는 함수가 있고, 타깃 독립 구간만 봐도 후보 비트플립 위치가 100만 개를 넘습니다. 하나당 30초씩 추론을 돌리면 409일이 걸립니다. 저자들은 4단계 프루닝 도구 Karnage를 만들어 이 탐색을 현실적인 시간으로 줄입니다.

프루닝 단계NVIDIA 후보AMD 후보
Stage 1: 네임스페이스 필터 (타깃 독립 함수)1,183,0081,326,122
Stage 1: Intel PT 필터 (실행된 명령)38,76942,996
Stage 3: 오프라인 컴파일 출력 비교1,176810
Stage 4: 실제 GPU 프로파일링생존생존
  • P1 타깃 독립성 · P2 출력 정상 + 느려짐 · P3 프롬프트/모델 전반의 일관된 느려짐 — 이 세 조건을 모두 만족하는 희귀한 비트만 "쓸모 있는 플립"으로 남깁니다. 대부분은 커널을 바꾸지 않거나, 크래시를 내거나, 출력을 망가뜨립니다.
  • Stage 3의 트릭: Triton의 오프라인 컴파일을 이용해 커널 런치를 가로채고 GPU 실행 전에 컴파일 결과만 비교합니다. CPU만으로 병렬 필터링이 가능해집니다.

실측 결과 — 4~16% 느려지고, 청구서는 최대 224만 달러

  • 실험 환경: Intel i7-4790 + DDR3 8GB / i7-8700 + DDR4 8GB, NVIDIA RTX 4090과 AMD RX 7900 XTX, vLLM 0.24/0.25.1 + Triton 3.6. 모델은 Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.3, DeepSeek-LLM-7B-chat.
  • 지연 증가: 단일 GPU 추론 서버에서 4~16%. 최대치는 DeepSeek-7B에 1,000개 요청을 몰아넣은 조건에서 관측됐습니다. 30회 반복 + Welch's t-test로 배치 추론의 고유 분산과 구분했습니다.
  • 비용 환산: H100을 시간당 4.50~10달러로 가정하면 GPU당 연 3.9천~8.76천 달러, 256-GPU 배포에서는 연 100만~224만 달러. 지연이 10% 늘면 연간 약 876시간(37일)의 서빙 용량이 사라진다는 계산입니다.
  • 더 나쁜 모드: 같은 도구로 출력까지 망가뜨릴 수 있습니다. 교차 벤더 조건에서 BERTScore가 25%까지 떨어졌습니다. 느려지는 것만으로도 충분히 나쁜데, 정확도 손상까지 가능하다는 뜻입니다.
  • 탐지 회피: 크래시도, 예외도, 정확도 하락도 없습니다. 관측되는 것은 "평소보다 조금 느린 서버"뿐입니다. 저자들은 이것이 기존 fault-injection 방어(DeepDyve, BitFlipScope)로 잡히지 않는다고 주장합니다.

어디까지 믿어야 하나 — "Rowhammer로 실제로 뒤집었다"는 아직 아니다

이 논문은 정직하게도 자기 주장의 경계를 여러 곳에서 긋습니다. 실무자 관점에서 가장 중요한 구분은 공격의 두 조각이 분리돼 있다는 점입니다.

  • 입증된 것 = 결과. libtriton.so의 특정 비트를 뒤집었을 때 커널이 느려지고, 그 커널이 캐시에 남아 재사용된다는 사실은 실제 하드웨어에서 측정됐습니다(4개 모델 · 2개 GPU · 30회 반복).
  • 입증되지 않은 것 = 트리거. 이 논문의 실험은 Karnage로 비트플립을 주입해 측정합니다. 메모리 마사징 → 공격자 행 할당 → 해머링으로 libtriton.so의 정확한 비트를 실제로 뒤집는 end-to-end 시연은 선행 Rowhammer 연구(PRowhammer 등)에 기대고 있습니다. 즉 "가능하다"는 논리적 확장이지, 이 논문 안에서 해머링까지 돌린 것은 아닙니다.
  • 플랫폼 한계: DDR3/DDR4에서만 실험했습니다. DDR5의 PRAC·TRR 환경, 데이터센터 GPU(H100 등), ECC 메모리 구성은 검증되지 않았습니다.
  • 측정의 한계: 표 VI를 보면 n=10 같은 작은 배치에서는 5개 지표 중 유의한 것이 0~2개뿐인 조합이 많습니다. 4% 수준의 저하는 구성에 따라 통계적으로 잡히지 않을 수 있습니다.
  • 완화책의 비용: 저자들이 제시하는 방어는 TRITON_ALWAYS_COMPILE과 세션마다 libtriton.so 재로드입니다. 캐시를 버리는 것이므로 커널 재컴파일 오버헤드를 상시 지불해야 합니다. "공짜 방어"가 아닙니다.

방어 — 정확도 모니터링이 아니라 '성능 기준선'을 감시해야 한다

  • 1순위: 커널 캐시 무결성. ~/.triton/cache의 커널 아티팩트와 libtriton.so의 해시를 배포 시점 기준선으로 고정하고, 변경·재컴파일을 감사합니다. Triton 커널 캐시 키에 컴파일러 바이너리 해시가 포함되도록 하는 것도 같은 방향의 개선입니다.
  • 2순위: 성능 기준선(performance baseline)을 보안 텔레메트리로 승격. TTFT·TPOT·tokens/s를 버전·모델·배치 크기별 기준선과 비교해, 설명되지 않는 지속적 하락을 알림으로 올립니다. 정확도 지표만 보는 모니터링은 이 공격에 구조적으로 눈이 먼 상태입니다.
  • 3순위: 세션 경계에서 컴파일러 상태 리셋. 신뢰 경계가 바뀌는 시점(새 테넌트, 재배포)마다 TRITON_ALWAYS_COMPILE=1 또는 라이브러리 재로드를 적용하고, 그 비용을 SLO에 미리 반영합니다.
  • 근본 방어: TRR/PRAC 같은 DRAM 완화책, ECC, 그리고 공동 테넌시에서 민감 워크로드를 물리적으로 분리. 결국 이 공격의 뿌리는 2014년부터 이어진 DRAM 무결성 문제입니다.

교육용 PoC — 벡터가 스칼라로 쪼개질 때 '얼마나 손해인가'를 계산해 본다

아래 코드는 실제 하드웨어를 건드리지 않습니다. (1) 128비트 벡터 로드가 스칼라 로드로 바뀌었을 때의 메모리 트랜잭션 증가를 모델링하고, (2) 컴파일러 라이브러리·커널 캐시의 무결성 기준선을 검사하는 방어자 쪽 루틴을 흉내 냅니다. 목적은 "정확도는 그대로인데 느려지는" 변화를 어떤 지표로 잡을 수 있는가를 이해하는 것입니다.

import hashlib, os, statistics

# 1) 벡터 폭이 4 -> 1로 쪼개질 때의 상대 비용 모델 (교육용 근사)
#    트랜잭션 수는 4배, 대역폭 효율은 1/4. 실제 지연은 캐시/코얼레싱에 따라 달라진다.
def relative_cost(vec_width, elements=4096):
    transactions = elements // vec_width
    return transactions * vec_width / 32.0   # 32B 섹터 기준 정규화

base = relative_cost(4)
broken = relative_cost(1)
print(f"vectorized: {base:.1f}  scalarized: {broken:.1f}  "
      f"modeled slowdown: {broken/base:.2f}x")
# 실측 논문 값은 1.04~1.16x -- 모델은 상한(최악)에 가깝다.
# 즉 '트랜잭션 4배'가 곧 '지연 4배'는 아니다. 메모리 수준 병렬성이 흡수한다.

# 2) 방어자 루틴: 컴파일러 바이너리 + 커널 캐시의 기준선 해시
def manifest(paths):
    out = {}
    for p in paths:
        if os.path.isfile(p):
            with open(p, "rb") as f:
                out[p] = hashlib.sha256(f.read()).hexdigest()[:16]
    return out

def audit(baseline, actual):
    drift = []
    for p, h in actual.items():
        if baseline.get(p) not in (None, h):
            drift.append((p, baseline[p], h))
    return drift

# 예: 배포 시점에 baseline.json 을 만들어 두고, 매 세션 시작 시 비교한다.
baseline = {"libtriton.so": "a1b2c3d4e5f60718"}
actual = {"libtriton.so": "a1b2c3d4e5f60718"}   # 비트플립이 있으면 해시가 달라진다
print("integrity drift:", audit(baseline, actual))

# 3) 성능 기준선 감시: 같은 배치 크기에서의 지속적 지연 증가만 경보
def drifting(samples, baseline_ms, threshold=1.05, windows=3):
    hits = sum(1 for s in samples[-windows:] if s > baseline_ms * threshold)
    return hits == windows and len(samples) >= windows

print("slowdown alarm:", drifting([100, 101, 104, 106, 107], baseline_ms=100))
print("normal jitter :", drifting([101, 99, 103, 100, 102], baseline_ms=100))
  • 첫 번째 교훈: 트랜잭션 수 4배가 지연 4배를 뜻하지는 않습니다. GPU의 메모리 수준 병렬성이 상당 부분을 흡수하기 때문에 실측은 4~16%에 그칩니다. 모델은 상한으로만 읽어야 합니다.
  • 두 번째 교훈: 해시 기준선은 비트플립 자체는 잘 잡지만, 공격자가 캐시를 정상 커널로 되돌리거나 기준선을 오염시키면 무력해집니다. 그래서 성능 기준선과 무결성 기준선을 함께 봐야 합니다.
  • 실습 과제: 배치 크기 n을 10/100/1000으로 바꿔 가며 위 drifting()의 오탐률을 재보세요. 논문의 표 VI처럼 작은 배치에서는 신호가 잡음에 묻힙니다 — 탐지기의 진짜 약점은 임계값과 표본 수입니다.

그래서 무엇이 남는가

  • 공격면이 '모델'에서 '툴체인'으로 넓어졌다. 지난 10년의 비트플립 공격은 가중치·활성값·페이지 테이블을 노렸습니다. 이 논문은 컴파일러의 최적화 결정이 새로운 표적임을 보여줍니다. 모델을 아무리 잘 지켜도, 모델을 실행 가능하게 만드는 소프트웨어가 공격면입니다.
  • "가용성 공격"은 탐지 체계의 사각지대다. 무결성·기밀성 중심의 보안 스택은 "느려졌다"를 사고로 분류합니다. 하지만 멀티테넌트 클라우드에서 4~16%의 지속적 손실은 곧 비용이며, 256-GPU 규모에서는 연 100만 달러가 넘습니다.
  • 공급망 관점의 교훈: 공유 라이브러리 하나(libtriton.so)가 수많은 서비스의 성능을 좌우합니다. 라이브러리 무결성 검증은 이제 보안팀의 일이지, DevOps의 편의 기능이 아닙니다.
  • 한국 실무 관점: 국내 클라우드·GPU 임대 사업자와 사내 LLM 추론 클러스터는 대부분 공동 테넌시와 공유 이미지를 씁니다. "정확도는 정상"이라는 대시보드 한 줄로 안심하는 순간, 이 공격은 보이지 않습니다. 성능 SLO를 보안 지표로 승격할 근거가 여기에 있습니다.
  • 연구 윤리: 저자들은 실제 피해 서비스 없이 자체 실험실 장비에서 측정했고, 완화책과 한계를 논문 안에 명시했습니다. 공격 코드는 공개하지 않았습니다 — 재현 도구보다 방어 지표를 먼저 배포한 셈입니다.
